# Feature Specification: 对齐 B 站网页版数据源（Web API Alignment）

**Created**: 2026-11-16  
**Status**: Draft  
**Input**: User description: "搜索回车进结果页无结果、手动点搜索按钮才行；搜索结果与官方网页/App 不一致；主页推荐、热门想与官方逻辑对齐" → 确认：以网页版为对齐基准，实现 WBI 签名；仅 phone 模块验证

## Overview

将 OhBili 的搜索与主页数据源对齐 B 站网页版逻辑：实现 WBI 接口签名机制与真实设备 Cookie（替换硬编码假 Cookie），使搜索结果、首页推荐、热门与网页版一致；并修复输入法回车搜索无结果的交互缺陷。登录用户自动获得与网页版登录态一致的个性化数据。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 回车搜索正常出结果 (Priority: P1)

用户在搜索页输入关键字后，无论是按输入法回车/搜索键还是手动点击"搜索"按钮，都进入搜索结果页并展示一致的搜索结果。

**Why this priority**: 当前回车无结果是明确的交互缺陷，用户高频触达，必须修复。

**Independent Test**: 搜索页输入任意关键字 → 按输入法回车 → 结果页展示与点击"搜索"按钮完全一致的结果列表。

**Acceptance Scenarios**:

1. **Given** 搜索页已输入中文关键字（经输入法候选上屏），**When** 按输入法回车/搜索键，**Then** 进入结果页且展示该关键字的搜索结果（非空、与按钮触发一致）
2. **Given** 搜索页已输入英文/数字关键字，**When** 按输入法回车，**Then** 结果与按钮触发一致
3. **Given** 输入框为空，**When** 按回车或点击搜索，**Then** 行为保持现状（默认词搜索或"关键字不能为空"提示）

---

### User Story 2 - 搜索结果对齐网页版 (Priority: P1)

用户搜索任意关键字，结果列表（条目数量、排序、内容）与 B 站网页版搜索该关键字的综合结果一致，不因风控出现空结果或降级结果。

**Why this priority**: 搜索是核心功能，当前假 Cookie + 无签名导致结果与官方差异明显且不稳定。

**Independent Test**: 对比同一关键字在应用与 B 站网页版的搜索结果：首页条目集合基本一致。

**Acceptance Scenarios**:

1. **Given** 应用已启动（签名密钥与设备 Cookie 就绪），**When** 搜索任意关键字，**Then** 返回结果条目与网页版综合排序结果一致
2. **Given** 已扫码登录，**When** 搜索，**Then** 携带登录 Cookie，结果与网页版登录态一致
3. **Given** 连续搜索多个关键字（正常频率），**When** 发起请求，**Then** 不出现因风控导致的空结果
4. **Given** 搜索结果分页加载，**When** 上拉翻页，**Then** 后续页结果与网页版翻页一致

---

### User Story 3 - 首页推荐对齐网页版 (Priority: P2)

首页"推荐"信息流与 B 站网页版首页推荐逻辑一致：未登录时为热门向推荐流，已登录时为个性化推荐流；支持持续下拉刷新出新内容。

**Why this priority**: 推荐流是首页核心体验，与官方逻辑对齐后内容池和刷新行为与网页版一致。

**Independent Test**: 对比应用推荐流与网页版首页推荐：内容风格/数量级一致，下拉刷新出不同内容。

**Acceptance Scenarios**:

1. **Given** 未登录状态，**When** 打开首页推荐，**Then** 展示与网页版未登录一致的热门向推荐流
2. **Given** 已扫码登录，**When** 打开首页推荐，**Then** 展示与网页版登录态一致的个性化推荐
3. **Given** 推荐流已展示，**When** 下拉刷新，**Then** 返回新的推荐内容（不重复上一屏）
4. **Given** 推荐流滚动到底，**When** 上拉加载，**Then** 持续追加内容不中断

---

### User Story 4 - 热门对齐网页版 (Priority: P2)

首页"热门"列表与 B 站网页版热门页一致：分页参数与条目数对齐官方，翻页内容连续。

**Why this priority**: 热门当前接口已与网页同源，仅需参数对齐与分页体验补齐。

**Independent Test**: 对比应用热门与网页版热门：首页条目集合与顺序一致，翻页连续。

**Acceptance Scenarios**:

1. **Given** 打开热门页，**When** 列表加载，**Then** 条目集合与网页版热门第一页一致
2. **Given** 热门列表滚动到底，**When** 上拉翻页，**Then** 下一页内容与网页版一致且不重复

---

### Edge Cases

- WBI 密钥获取失败（网络异常/接口变更）：降级为不签名请求并记录日志，页面展示可重试提示，不崩溃
- 设备 Cookie（buvid3 等）获取失败：使用本地生成的随机兜底值，功能不中断
- 搜索/推荐返回风控码（如 -412）：提示"请求过于频繁，请稍后再试"，不展示空白页
- 输入法组合输入未上屏时按回车：按已上屏内容搜索；无已上屏内容走默认词/空提示逻辑
- 登录凭证过期（nav 校验失败）：自动清除登录态，推荐/搜索退化为未登录数据，无异常

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 实现 B 站 WBI 签名机制（从用户导航接口获取密钥、生成签名参数），供需要签名的 web 接口使用
- **FR-002**: 系统 MUST 使用真实设备 Cookie（通过官方指纹接口获取 buvid3 等），替换现有硬编码假 Cookie；已登录时叠加登录 Cookie
- **FR-003**: 搜索页 MUST 修复回车触发逻辑：输入法回车/搜索键与点击"搜索"按钮产生完全一致的搜索行为与结果
- **FR-004**: 搜索 MUST 使用 WBI 签名的 web 搜索接口，结果对齐网页版综合排序；支持分页且与网页版一致
- **FR-005**: 首页推荐 MUST 对齐网页版推荐流逻辑：未登录热门向、已登录个性化，刷新出新内容、加载不中断
- **FR-006**: 首页热门 MUST 对齐网页版分页参数与条目顺序
- **FR-007**: Cookie/密钥/签名失败时 MUST 有降级策略与友好提示，任何场景不崩溃、不白屏
- **FR-008**: 登录态变化（登录成功/凭证过期清除）后，推荐与搜索数据 MUST 在下次请求时自动使用新的 Cookie 状态

### Key Entities *(include if feature involves data)*

- **WBI 密钥对（WbiKeys）**: 从用户导航接口获取的图片密钥（img_key/sub_key），派生混合密钥用于参数签名
- **签名参数（WbiSignature）**: 附加在请求查询串上的签名数据（w_rid、wts 等）
- **设备 Cookie（DeviceCookies）**: 标识设备的会话数据（buvid3/buvid4 等），通过官方指纹接口获取，持久化保存
- **搜索结果（沿用现有 SearchVideo 实体）**: 对齐网页版后字段语义不变，仅数据源修正

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 回车与按钮触发搜索的结果 100% 一致（同关键字、同页码）
- **SC-002**: 同一关键字下，应用搜索首页结果与网页版前 20 条重合度 ≥80%
- **SC-003**: 连续 10 次搜索/刷新操作不触发风控空结果
- **SC-004**: 推荐流连续 5 次下拉刷新均返回不重复内容
- **SC-005**: 所有异常场景（断网、密钥失败、风控）有提示且应用不崩溃

## Assumptions

- 仅在 phone 模块验证；网络层改动位于 common（共享 HAR），tablet 自然继承但不在本轮验证范围
- B 站网页版 WBI 签名算法保持公开可逆向的标准实现（社区广泛使用）；若官方调整算法导致签名失效，属外部依赖风险，需降级策略兜底
- 用户已扫码登录（qr-login 功能）后，登录 Cookie 可用于个性化数据；未登录用户获得与网页版未登录一致的数据
- 搜索结果页 UI 布局本轮不改动，仅数据源与触发逻辑对齐
- 现有 UI 组件（PopularItemView 等）沿用，字段映射在数据层适配
