# Feature Specification: B站扫码登录（QR Login）

**Created**: 2026-11-15  
**Status**: Draft  
**Input**: User description: "登录界面输入手机号后点击获取验证码没有效果" → 经确认改为实现扫码登录，替换现有半成品短信登录页

## Overview

在 OhBili（phone 模块）中实现 B 站扫码登录：登录页展示二维码，用户使用 B 站 App 扫码确认后完成登录。登录态持久化保存（重启应用不丢失），动态页在已登录状态下展示用户昵称与头像。现有无法使用的短信登录 UI 被移除。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 展示二维码登录页 (Priority: P1)

用户从动态页点击"登录"进入登录页，页面显示 B 站登录二维码及提示文案"请使用 B 站 App 扫码登录"。

**Why this priority**: 二维码展示是扫码登录的最小可用切片，没有它后续一切流程无从谈起。

**Independent Test**: 在设备上打开动态页 → 点击"登录" → 进入登录页，可见二维码图片与提示文案。

**Acceptance Scenarios**:

1. **Given** 用户未登录，**When** 在动态页点击"登录"按钮，**Then** 跳转到登录页，页面展示二维码和扫码提示
2. **Given** 登录页已展示二维码，**When** 二维码成功生成，**Then** 二维码在 3 秒内可见且可扫描

---

### User Story 2 - 扫码并确认登录 (Priority: P1)

用户使用 B 站 App 扫描二维码并在手机上确认登录后，应用检测到登录成功，保存登录凭证并给出成功反馈（如提示/自动返回）。

**Why this priority**: 完成扫码→登录的核心闭环，是本功能的核心价值。

**Independent Test**: 用 B 站 App 扫描页面二维码并确认 → 登录页提示登录成功 → 返回动态页显示已登录状态。

**Acceptance Scenarios**:

1. **Given** 登录页已展示二维码，**When** 用户用 B 站 App 扫码并确认登录，**Then** 应用在 5 秒内检测到登录成功并给出成功反馈
2. **Given** 用户已扫码但未确认，**When** 轮询到"已扫码"状态，**Then** 页面提示"已扫码，请在手机上确认"
3. **Given** 登录成功，**Then** 登录凭证（cookie、token 等）被持久化保存

---

### User Story 3 - 登录态持久化与用户信息展示 (Priority: P2)

用户登录成功后重启应用，登录态依然有效；动态页展示用户昵称与头像。

**Why this priority**: 登录态不持久会导致每次启动都要重新扫码，体验不完整；展示用户信息让用户直观确认登录身份。

**Independent Test**: 扫码登录成功 → 杀掉应用重新打开 → 动态页仍显示已登录且展示昵称与头像。

**Acceptance Scenarios**:

1. **Given** 用户已登录，**When** 重启应用进入动态页，**Then** 不再显示"未登录"提示，展示用户昵称与头像
2. **Given** 用户已登录，**When** 拉取用户信息，**Then** 昵称与头像正确显示（与 B 站账号一致）

---

### User Story 4 - 二维码过期与刷新 (Priority: P2)

二维码超过有效期（约 180 秒）未扫码时，页面提示二维码已过期，用户可点击刷新获取新二维码。

**Why this priority**: B 站二维码有时效限制，无过期处理会导致页面停留在死码上，用户困惑。

**Independent Test**: 停留登录页超过二维码有效期 → 页面显示"二维码已过期"与刷新入口 → 点击后重新生成二维码。

**Acceptance Scenarios**:

1. **Given** 登录页二维码展示超过有效期未被扫码，**When** 轮询返回过期状态，**Then** 二维码上出现"已过期"提示及"点击刷新"入口
2. **Given** 二维码已过期，**When** 用户点击刷新，**Then** 生成新二维码并重新开始轮询

---

### Edge Cases

- 网络中断时轮询失败：页面提示网络异常，恢复后自动重试轮询，不崩溃
- 登录接口返回异常数据（如字段缺失）：按未登录处理，给出错误提示，不崩溃
- 用户在扫码确认前退出了登录页：轮询随页面销毁而停止，不产生泄漏或异常
- 同一二维码被重复刷新：始终只以最新一次生成的二维码为准

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 登录页 MUST 展示 B 站扫码登录二维码，并附带"请使用 B 站 App 扫码登录"类提示文案
- **FR-002**: 系统 MUST 轮询扫码状态，能够区分"未扫码 / 已扫码待确认 / 已确认成功 / 二维码过期"四种状态并分别反馈
- **FR-003**: 登录成功后系统 MUST 持久化保存登录凭证（cookie、token），应用重启后登录态保持
- **FR-004**: 已登录状态下，动态页 MUST 展示用户昵称与头像（从 B 站用户信息接口获取）
- **FR-005**: 二维码过期后，用户 MUST 能通过点击刷新获取新二维码
- **FR-006**: 现有短信登录 UI MUST 从登录页移除（网络层已有的短信接口代码保留不动）
- **FR-007**: 用户离开登录页时 MUST 停止扫码状态轮询，回到页面后重新开始
- **FR-008**: 轮询或登录过程中发生网络/接口错误时，页面 MUST 展示友好错误提示且不崩溃

### Key Entities *(include if feature involves data)*

- **登录凭证（LoginCredentials）**: 扫码确认成功后获得的会话数据，包含 cookie（如会话 ID、用户 ID 标识、CSRF token）与刷新 token；需持久化存储
- **扫码状态（QrStatus）**: 二维码当前生命周期状态：未扫码、已扫码待确认、已过期、登录成功
- **用户信息（UserInfo）**: 已登录用户的昵称与头像地址，由用户信息接口返回

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 从进入登录页到二维码可见，正常网络下不超过 3 秒
- **SC-002**: 扫码确认后 5 秒内应用给出登录成功反馈
- **SC-003**: 登录成功后重启应用，100% 保持登录态且动态页正确展示昵称与头像
- **SC-004**: 二维码过期、断网等异常场景下应用不崩溃，且有明确用户提示

## Assumptions

- 仅在 phone 模块实现；tablet 模块登录保持现状（后续单独处理）
- 用户设备可正常访问 B 站服务器，且已安装 B 站 App 用于扫码
- B 站 Web 端扫码登录接口（生成二维码 + 轮询状态）可供第三方客户端调用；若 B 站风控策略变化导致接口不可用，属外部依赖风险
- 登录后动态内容本身仍为"待实现"，本功能仅覆盖登录闭环与用户信息展示
- 现有网络层（retrofit + taskPool）与 AppStorage 的 `isOhBiliLoggedIn` 标志沿用，短信登录相关网络代码保留但不接 UI
